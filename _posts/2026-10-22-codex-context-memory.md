你让 Codex 排查一个订单接口的重复下单问题。它读了路由、Service、数据库访问代码，又执行了几轮测试。半小时后，它突然再次搜索刚才看过的文件，还需要你重新提醒：“这次不能修改接口字段。”

你可能会想：聊天记录还在，它为什么不记得？

理解这个现象，要先分清三件事：**客户端保存了什么、本次模型能看到什么、哪些信息已经被压缩成了另一种表示。** 它们并不总是一致。

沿着这个开发场景，我们先理解“短期记忆”是怎样工作的，再看上下文快满时如何压缩，以及 Codex 与 Claude Code 在这些机制上的差别。

> 本文讨论一次会话中的短期上下文。产品细节以 2026 年 10 月的公开文档和代码为参考，具体行为取决于客户端版本与配置；文中的预算数字仅用于教学。

## 1. “短期记忆”是什么：一张有限大小的工作台

### 1.1 先认识模型与 Agent

**大语言模型（LLM）**可以根据输入材料生成后续内容，例如解释代码、提出修改方案，或给出一次工具调用。

**Agent** 则是在模型外面加上工具和执行循环的软件系统。以编码 Agent 为例，一轮工作通常是：

1. 客户端把任务、指令和已有材料交给模型。
2. 模型提出下一步，例如读取文件或运行测试。
3. 客户端执行工具，把结果放回上下文。
4. 模型根据新增结果继续行动，直到给出答案或完成任务。

模型负责判断下一步，客户端负责提供上下文、执行工具和管理会话。因此，“Codex 怎么记住任务”既涉及模型，也涉及包围模型的这层软件，通常称为 **Agent harness**，可以理解为 Agent 的运行框架。

### 1.2 上下文就是本次推理可用的工作材料

**上下文（context）**是本次模型推理能使用的输入与相关会话状态。你可以把它想成一张工作台：任务要求、代码片段、测试输出，都要放到台面上，模型才能直接使用。

**Token** 是模型处理信息时使用的计量单位。它不等于一个汉字、一个英文单词或一个字节；一段代码和同长度自然语言的 token 数也可能不同。

**上下文窗口（context window）**则是这张工作台的容量限制。不同模型的容量不同，输入、输出，以及部分模型的推理 token 还需要按各自规则共同计入预算。具体限制应看对应模型文档。[OpenAI：会话状态与上下文窗口](https://developers.openai.com/api/docs/guides/conversation-state)

### 1.3 不要混淆三种“记住”

| 信息放在哪里 | 用后端概念类比 | 对当前任务意味着什么 |
| --- | --- | --- |
| 模型参数 | 部署好的程序所具备的一般能力；仅作类比 | 知道常见编程语言与技术概念，不等于知道你刚才的要求 |
| 当前上下文 | 一次处理流程正在使用的请求上下文 | 模型能直接据此推理，但容量有限 |
| 外部文件、任务笔记和会话记录 | 文件系统、数据库或日志 | 可以长期保存，需要被读取或检索后才能成为当前工作材料 |

正常的一次聊天不会自动修改模型参数。你告诉它“订单号必须全局唯一”，通常是把一条约束加入当前会话；这和重新训练模型是两回事。

后面所有讨论都围绕第二层：**怎样让有限的当前上下文，支撑一个可能持续很久的任务。**

## 2. Codex 的上下文里，为什么不只有聊天消息

### 2.1 工具调用会让历史迅速变长

假设你让 Agent 检查重复下单问题，一段简化的历史可能是：

```text
用户：检查重复提交订单会不会生成两笔订单。
助手发起工具调用：读取 OrderService.java。
工具返回：文件内容。
助手发起工具调用：运行重复请求测试。
工具返回：断言失败，返回了两个不同的订单号。
助手：怀疑缺少幂等处理，继续检查事务边界。
```

**工具调用**是模型提出的操作请求，**工具返回**是客户端交回模型的执行结果，也可能包含超时、拒绝或未启动等错误。模型提出“运行测试”不能证明测试已执行；判断结果要看进程是否启动、退出码和测试报告。命令执行成功，也不一定等于所有测试通过。

为了继续工作，运行框架需要维护这类有顺序的会话项。它们可能包括用户消息、助手输出、工具调用、工具结果，以及接口支持的推理相关项。

这里的“推理相关项”不代表客户端能拿到模型完整、可读的内部思考过程。接口可能只提供推理摘要或不透明状态；普通聊天界面显示的文字也不是全部协议数据。[OpenAI：Responses API 的输入与输出项](https://developers.openai.com/api/reference/resources/responses/methods/compact)

### 2.2 系统指令和工具定义是另一部分输入

除了对话历史，请求还需要描述：

- **系统或开发者指令**：Agent 的角色、工作规则与行为约束。
- **项目指令**：例如 `AGENTS.md` 中的构建方式、代码约定和操作边界。
- **工具定义**：工具名称、参数结构和用途，让模型知道有哪些操作可选。

从请求组织方式看，这些内容可能位于独立字段，也可能以特定消息或上下文片段注入。**单独管理不意味着不占上下文预算。** 工具定义尤其容易被忽略：工具越多、参数说明越长，留给业务材料的空间就可能越少。

Codex 官方提示指南介绍了项目 `AGENTS.md` 的注入方式；具体请求结构仍应以客户端版本为准。[OpenAI：Codex Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)

### 2.3 为什么下一次请求还需要历史

如果只给模型一句“那就按第二种方案改”，却不提供之前讨论的两种方案，它无法可靠知道“第二种”指什么。

在**客户端管理历史**的模式下，常见做法是每轮发送当前有效的历史，再追加新消息或工具结果。注意，是“当前有效的历史”，经过压缩后就未必还是最初的完整历史。

但“每次都把全部上下文重新发送”不能当成所有 API 的协议规则。有的接口支持用 `previous_response_id` 等标识引用已有状态，客户端只提交新增输入。网络传输可以简化，模型仍需要可用的前文；这也不意味着前文的 token 成本自动消失。[OpenAI：Conversation state](https://developers.openai.com/api/docs/guides/conversation-state)

后端工程师可以把它理解为两种会话状态管理方式：一种由调用方显式携带状态，另一种通过标识让服务端找到状态。两者都需要解决“有效状态越来越大”的问题。

## 3. 前缀缓存：省重复计算，不会让窗口变大

假设两次请求的开头完全一致：

```text
请求 A：[固定指令][工具定义][已有历史][问题 A]
请求 B：[固定指令][工具定义][已有历史][问题 A][回复 A][问题 B]
```

第二次请求之前有一大段已经处理过的内容。**前缀缓存（prompt caching）**会在满足条件时复用相同前缀的模型计算，减少重复处理的开销。

这里的**前缀**就是从输入开头开始、保持一致的那部分内容。它不是按关键词做相似匹配；还要满足模型、缓存边界、有效期等条件。把开头的指令改写了，后面的公共内容也未必能命中原来的缓存。

缓存也不是“把上次答案拿来直接返回”。模型仍会结合新的后缀生成内容。净成本收益取决于命中情况、缓存读写定价和复用次数，不能把“相同前缀”直接等同于“免费”。[OpenAI：Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

![前缀缓存与上下文压缩的作用区别](02-cache-vs-compaction.png){: width="1680" height="1120" }

*图 2：缓存复用计算，压缩缩短工作材料。图中的 token 数只是教学示例。*

最容易混淆的一点是：**缓存命中的内容仍属于模型的上下文，仍然受窗口容量限制。**

可以类比数据库执行计划缓存：复用某些准备工作，不等于查询需要处理的逻辑数据消失了。这个类比只用于说明“复用计算”和“缩小输入”是两个维度。

因此，即使缓存效果很好，长任务仍可能把上下文窗口填满。接下来就需要压缩。

## 4. 为什么要提前压缩，而不是等窗口彻底用完

除了已经放进去的内容，Agent 还需要为接下来的回答和操作预留空间。

假设一个教学模型的窗口是 128,000 tokens，我们粗略分配：

| 项目 | 教学预算 |
| --- | ---: |
| 指令与工具定义 | 8,000 |
| 当前历史 | 95,000 |
| 本轮新增输入 | 4,000 |
| 为输出、推理及后续工具交互留的余量 | 16,000 |
| 合计 | 123,000 |

虽然表面上尚未达到 128,000，继续读取一个较大的文件就可能把余量吃完。压缩请求本身也需要容纳待处理材料，因此不适合等到完全塞不下时才处理。

可以用一个规划公式来理解：

```text
已有上下文 + 新增输入 + 后续工作余量 ≤ 本次可用窗口
```

这不是模型服务的精确计费公式，也不是 Codex 源码中的统一触发算法。不同模型对输出、推理 token 和工具交互的约束不同，但“提前留出工作空间”这个原则是通用的。

Codex 配置参考提供了 `model_auto_compact_token_limit`，用于设置自动压缩阈值，未设置时使用模型默认值。它是触发策略，不是扩大模型容量的开关。[Codex：Configuration Reference](https://developers.openai.com/codex/config-reference/)

## 5. 上下文压缩，究竟压缩了什么

### 5.1 把过程改写成能继续工作的状态

**上下文压缩（compaction）**的目标，是用更短的表示承接后续任务。

原来可能有几十次搜索和读取：

```text
搜索幂等相关实现。
读取订单 Service。
读取支付回调。
运行并发测试，失败。
继续检查唯一索引。
……
```

压缩后，更有用的工作材料可能是：

```text
目标：修复重复提交订单生成两笔订单的问题。
已确认：客户端已有 request_id，服务端未强制其唯一。
定位：OrderService.create，订单表目前没有相应唯一约束。
约束：不能修改现有接口字段。
验证：并发重复提交测试失败；尚未验证修复方案。
下一步：确认 request_id 的业务作用域，再设计唯一约束与冲突处理。
```

这段摘要省去了探索过程，却保留了目标、事实、约束、证据状态和下一步。它更像一份交接记录。

这里存在一个无法回避的取舍：今天看似不重要的细节，明天可能变成关键证据。只保留有限信息，就有遗漏风险；这和 ZIP 一类可还原全部原文的无损压缩不同。

### 5.2 两类常见表示：文字摘要与不透明状态

![文字摘要路径与不透明状态路径](03-compaction-paths.png){: width="1680" height="1120" }

*图 3：应区分压缩由谁组织、返回什么表示，以及后续如何续接。*

**第一类是文字摘要。** 客户端组织一次总结请求，让模型生成文字，再把摘要和选定的消息组成新的活动历史。人可以阅读摘要，也可以在产品提供相应入口时进行复核或编辑。

Codex 的开源代码中存在这种文字摘要重建路径。一个容易误解的词是“本地压缩”：**本地可以只是指客户端负责组织流程，不代表模型在本机离线运行。** 摘要完全可能仍由远端模型生成。[Codex 开源代码：compact.rs](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs)

**第二类是不透明状态。** OpenAI 的独立 `/responses/compact` 接口返回一个结构化压缩窗口，其中包含带有 `encrypted_content` 的压缩项，也可能包含保留的消息。这个封装项不是供人阅读和改写的普通摘要。

对于这个独立接口，应用应把返回的窗口作为规范结果继续传入，不能只挑一个加密字段、解码猜测含义，或自行删掉其余返回项。需要新增要求时，在后续输入中追加。[OpenAI：独立 Compaction 接口](https://developers.openai.com/api/docs/guides/compaction)

不透明只说明应用无法按普通文本理解其内部表示，**不构成“所有历史都无损保存”的保证**。

### 5.3 服务端压缩，也有不同接入方式

除了显式调用独立压缩接口，OpenAI API 还支持在普通请求中配置 `context_management` 与 `compact_threshold`，由服务端在达到阈值时触发压缩。这两种接入模式的历史维护规则并不完全一样，不能混用裁剪规则。[OpenAI：Server-side compaction](https://developers.openai.com/api/docs/guides/compaction)

对使用编码产品的开发者来说，通常不必自己处理这些协议项；对开发 Agent 框架的工程师来说，必须按实际接入模式管理状态。

还要区分产品层与 API 层：**API 提供某项能力，不等于所有 Codex 客户端版本都以相同方式启用了它。**

### 5.4 接入不同模型时，先确认压缩能力

选择哪条压缩路径，要同时看**客户端实现、提供方接口能力和实际配置**。

在支持的配置中，客户端可以把历史交给服务端压缩；如果采用普通模型调用来总结历史，则会得到文字摘要。缺少兼容的服务端压缩接口时，能否改用文字摘要，取决于框架是否实现了这条路径，不能假定它一定会自动回退。

例如，通过自定义模型服务接入 Claude、Gemini 等模型时，要检查所用客户端和网关支持哪些协议。**模型能回答代码问题，不等于这套接入已经支持历史压缩、工具调用和会话恢复。** 因而，“OpenAI 模型一律服务端压缩、其他模型一律本地摘要”不能作为通用规则。

## 6. 压缩之后，哪些东西还在

先回答一个常见问题：**从模型当前上下文中移除，不等于从磁盘或聊天记录中永久删除。** 反过来，即使原始记录仍然保存着，模型也不一定会自动检索它。

对于一种典型的文字摘要重建方式，可以这样理解：

| 内容 | 压缩后可能如何处理 | 对开发任务的影响 |
| --- | --- | --- |
| 当前目标、已确认事实、未完成事项 | 写入文字摘要 | 能继续工作，但摘要可能遗漏或概括错误 |
| 一部分近期用户消息 | 在预算内保留 | 较新的要求更容易原样留存，仍不保证全部保留 |
| 当前有效的项目上下文和规则 | 从配置或文件重新构建、注入 | 要把长期约束放在明确的项目规则中 |
| 系统指令和工具定义 | 按本轮请求机制继续提供 | 这些内容仍然需要预算，并非免费空间 |
| 较早的助手回复、工具调用与原始结果 | 可能不再逐条携带 | 具体文件内容、命令和错误细节可能需要重新获取 |

这张表是帮助理解的常见模式，不是所有产品、所有压缩路径的固定返回格式。

### “约 20k tokens”到底指什么

Codex 的文字摘要重建实现 `compact.rs` 定义了常量 `COMPACT_USER_MESSAGE_MAX_TOKENS = 20_000`。文字摘要重建函数从较新的用户消息开始，按近似 token 数选择，在预算边界处可能截断，然后加入摘要；项目初始上下文另有重建逻辑。[Codex：文字摘要重建实现](https://github.com/openai/codex/blob/main/codex-rs/core/src/compact.rs)

所以，准确理解应该是：

- 它是**这条重建路径中保留用户消息的预算**，不是整个上下文窗口大小。
- 它不意味着“最近 20k tokens 的全部对话原封不动保留”。工具输出、助手回复与用户消息不是同一类项。
- 它也不意味着“压缩完成后总共只剩 20k tokens”。摘要、重新提供的规则和其他上下文还要另算。
- 不能把这个源码常量直接套到服务端封装结果、其他产品或未来版本上。

理解预算的对象，比记住数字本身更有价值。

## 7. Codex 与 Claude Code 的差别在哪里

两者都要在有限上下文中维持任务连续性。比较时，重点看历史被替换成什么、后续怎样承接，以及哪些材料会重新加载。

### 7.1 Claude Code 的会话压缩与子 Agent 委派

Claude Code 有两种容易混淆的机制：

**会话压缩**是在主会话接近限制时管理旧内容，包括清理较早的工具输出，以及按需总结对话。用户可以用 `/compact` 并指定关注点，例如 `/compact focus on the API changes`。

**子 Agent** 则在自己的上下文窗口中工作，将工作结果摘要交回主会话。它主要用来把大段检索、阅读或专项分析隔离出去。[Claude Code：工作原理与上下文管理](https://code.claude.com/docs/en/how-claude-code-works)

可以用两个开发场景区分：

- 主会话排查订单问题太久，需要缩短已有历史：这是会话压缩。
- 把“查清支付 SDK 的重试语义”交给另一个 Agent，只拿回结论与证据：这是任务委派。

区分它们的关键在于目的：**会话压缩是在缩短已有历史，子 Agent 委派是在划分工作及其上下文。** 子 Agent 返回摘要，不能用来证明自动压缩的内部执行方式。

### 7.2 压缩后也会重新加载部分材料

Claude Code 当前文档说明，压缩后会重新注入项目根目录的 `CLAUDE.md` 等材料，并重新读取部分近期文件；嵌套规则和其他内容有各自的加载规则。具体保留策略带有版本差异。[Claude Code：What survives compaction](https://code.claude.com/docs/en/context-window#what-survives-compaction)

这说明，压缩后能继续工作，可能同时依赖摘要和重新取得的外部材料，而不是单靠一段摘要保存所有信息。

### 7.3 从使用角度看两者的差别

下表比较两种产品，并在 Codex 一栏区分文字摘要路径与兼容的服务端压缩路径。

| 比较维度 | Codex | Claude Code |
| --- | --- | --- |
| 怎样承接较早的历史 | 文字摘要路径重建摘要与选定消息；兼容的服务端路径可返回不透明压缩状态 | 用对话摘要承接旧历史，并按规则重新加载部分材料 |
| 人能否直接读懂压缩表示 | 文字摘要可读；服务端不透明项不适合人工解析或改写 | 文字摘要可理解，但能否直接编辑仍取决于产品入口 |
| 怎样继续提供规则与工具 | 结合当前有效的项目上下文、指令和工具定义重建请求 | 根目录项目指令等重新注入，部分材料按需加载 |
| 子 Agent 是否等同于压缩机制 | 不能把任务委派与历史压缩等同 | 主会话压缩与子 Agent 的独立上下文是不同机制 |
| 共同局限 | 压缩不能保证所有原始细节都继续可用 | 同样可能遗漏细节，需要外部记录与核验 |

如果你使用的是不透明状态路径，应用的职责是按协议完整续传状态；如果得到的是文字摘要，则可以检查它是否保留了目标、约束和未完成事项。**可读性与信息保真度是两个指标**，不能单凭摘要形式判断哪种产品更可靠。

从工程设计上看，压缩、结构化任务笔记和子 Agent 委派可以配合使用：压缩控制已有历史的大小，笔记提供可恢复的外部状态，子 Agent 则隔离某一项工作的详细过程。[Anthropic：Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

## 8. 一个最小示例：历史还在，活动上下文已经换了

下面的 Python 示例不调用任何模型，只演示“摘要 + 近期用户消息”如何替换当前工作材料。

事件结构采用简化的教学格式，摘要由人工写入。它用于观察上下文如何变化；接入真实模型时，需要使用对应 API 的协议格式。

```python
def rebuild_context(events, summary, keep_users=2):
    if keep_users < 1:
        raise ValueError('keep_users must be positive')
    recent_users = [e for e in events if e['kind'] == 'user'][-keep_users:]
    return [{'kind': 'summary', 'text': summary}, *recent_users]


history = [
    {'kind': 'user', 'text': '排查重复提交订单的问题。'},
    {'kind': 'tool_call', 'text': '读取 OrderService.java'},
    {'kind': 'tool_result', 'text': '读取到 300 行代码……'},
    {'kind': 'tool_call', 'text': '运行重复请求测试'},
    {'kind': 'tool_result', 'text': '测试失败：生成两个不同订单号。'},
    {'kind': 'assistant', 'text': '检查 request_id 与唯一约束。'},
    {'kind': 'user', 'text': '不能修改现有接口字段。'},
    {'kind': 'assistant', 'text': '继续确认 request_id 的业务作用域。'},
]
summary = '目标：修复重复下单。已知：重复请求测试失败。待确认：request_id 作用域。'
active = rebuild_context(history, summary)

assert len(active) == 3
assert active[-1]['text'] == '不能修改现有接口字段。'
assert not any(e['kind'] == 'tool_result' for e in active)
assert any(e['kind'] == 'tool_result' for e in history)

print(f'原始历史：{len(history)} 项；新上下文：{len(active)} 项')
for event in active:
    print(f"{event['kind']}: {event['text']}")
```

完整文件为 `examples/context_demo.py`，包含在[完整学习包](#download)中。解压后进入 `codex-context-memory/`，使用 Python 3 执行：

```bash
python3 examples/context_demo.py
```

预期输出：

```text
原始历史：8 项；新上下文：3 项
summary: 目标：修复重复下单。已知：重复请求测试失败。待确认：request_id 作用域。
user: 排查重复提交订单的问题。
user: 不能修改现有接口字段。
```

观察两个细节：

第一，旧的 300 行代码和测试原始输出已经不在 `active` 中，但仍在 `history` 中。后续若只向模型提供 `active`，就不能假设它还能逐字引用旧输出。

第二，消息条数变少不等于测得了 token 压缩率。这个示例没有调用模型或 tokenizer（把内容转换成 token 的工具），因此只能演示历史重建，不能用于评估摘要质量或产品性能。

实际框架还要继续提供本轮有效的指令与工具定义，正确维护调用与结果的对应关系，并按所用接口的规则处理不透明项。**不能把这个教学函数直接当成生产环境的通用压缩器。**

## 9. 压缩为什么可能让 Agent 重复工作，甚至判断失准

### 9.1 搜索过什么，可能没有进入摘要

原始过程里，Agent 搜过 `request_id`、`idempotent`、`duplicate`，还检查过三个目录。摘要若只留下“继续检查幂等实现”，下一轮就可能再次搜索。

这通常是浪费时间，却不一定是错误。有时文件已经变化，重新读取反而是合理核验。判断是否无效重复，要看它是否在重复获取同一状态、是否产生了新证据。

可以把容易重复的关键调查写清楚：

```text
已检查：service/order、repository/order、支付回调。
当前结论：截至提交 abc123，以上范围未找到服务端幂等约束。
未检查：历史迁移脚本和异步补偿任务。
```

这里的“截至哪个版本、查过哪些范围”很重要。“在这些目录没找到”不能概括成“整个系统没有”。

### 9.2 摘要可能把“怀疑”写成“确认”

原始记录是“初步怀疑数据库连接池耗尽，还没检查池指标”，摘要却变成“根因是连接池耗尽”。后续 Agent 就可能围绕一个未证实的前提继续修改。

建议让任务记录明确区分：

| 状态 | 应该怎样写 |
| --- | --- |
| 已确认事实 | 给出文件、日志、命令或测试证据 |
| 当前推断 | 写明依据，并保留“待验证”状态 |
| 未解决问题 | 写出缺少什么信息，以及下一步如何取得 |

同样，“已经修改代码”“本地测试通过”“已部署”“线上问题消失”是四种不同结论。压缩时不能把它们合并成一个“已完成”。

### 9.3 多次压缩可能累计遗漏，但不必然越压越差

假设一条约束在第一次摘要中被省略，下一次压缩又只依赖摘要与近期消息，这条约束就很难凭空恢复。

因此，多次有损总结可能带来累计信息损耗。但它并不是“压缩次数越多，准确率一定按比例下降”：摘要质量、任务结构、外部笔记和后续重新验证都会影响结果。

更实用的问题是：**关键事实有没有可靠的外部来源，Agent 需要时能否重新取得并核对？**

### 9.4 重复读取与重复执行，风险不同

重复读取文件通常只是成本问题；重复扣款、重复发布配置或重复发通知，可能产生真实副作用。

因此，不能只在摘要里写一句“刚才好像执行过”。对有副作用的操作，应使用任务编号、幂等键、外部执行记录和状态查询来判断是否已完成。这是后端工程中熟悉的“幂等”与“事实来源”原则，在 Agent 场景同样适用。

**摘要是工作线索，外部系统的执行状态才是相应操作是否完成的证据。**

### 9.5 一次重复行为，也不能直接证明发生了压缩

重复搜索还可能来自文件变化、检索结果不充分、工具失败，或模型没有正确利用已有信息。

如果要排查“是不是压缩造成的”，应查看产品是否出现压缩提示、上下文用量是否发生变化、当前有效摘要是否遗漏了关键内容。没有这些信息时，结论应停留在“可能”，不能只凭现象确认原因。

## 10. 怎样让长任务做得更稳

### 10.1 一条会话围绕一个主要目标

“修复订单幂等”与“规划下一次旅行”放在同一条会话里，会让上下文同时混入两套无关目标。

更好的任务边界是：目标明确、约束一致、验证标准相同。对订单幂等问题，从调查到实现再到验证，保持连续会话往往有价值；不需要机械地把每个小步骤都拆成新会话。

当任务自然分成几个独立专题时，再拆成多个会话，并写好交接信息。拆分能减少无关材料，也会带来信息传递成本；需要频繁共享同一组细节的步骤，未必适合硬拆。

### 10.2 在阶段边界留下可恢复的任务记录

例如完成定位后、开始实现前，用一小段 Markdown 记录：

```markdown
## 当前目标
修复相同 request_id 的重复下单，保持现有接口字段。

## 已确认事实
- 入口：OrderController.create。
- 核心逻辑：OrderService.create。
- 重复请求测试失败，返回两个不同订单号。

## 决策与理由
- 暂不增加接口字段，优先复用现有 request_id。
- 唯一约束尚未定稿，先确认 request_id 的业务作用域。

## 已完成 / 未完成
- 已完成：定位与失败用例。
- 未完成：实现、迁移评估、修复后测试、部署及线上验证。

## 证据与下一步
- 测试命令、完整结果、相关文件位置另存。
- 下一步：确认作用域，再评估唯一索引与冲突返回语义。
```

这些名称只是教学示例，真正使用时要替换成实际路径、命令与版本。

这种笔记既能给同一个 Agent 恢复工作，也适合交给另一条会话或另一位工程师。写完仍应让接手方读取它，并核对当前代码状态。

### 10.3 稳定规则放项目指令，临时进度放任务笔记

“测试怎么运行”“哪些操作需要审批”“公共接口如何保持兼容”，适合放在项目指令中，例如 Codex 的 `AGENTS.md`。

“当前怀疑哪个函数”“哪次测试失败”“接下来要验证什么”，适合放在任务笔记里。不要把每次排障日志都塞进长期规则文件，否则每个任务都要携带大量无关内容。

Claude Code 的 `CLAUDE.md` 也是承载持久项目指令的机制之一。当前文档明确说明项目根目录文件会在压缩后重新读取，但临时写在聊天里的要求未必同样持久。[Claude Code：How Claude remembers your project](https://code.claude.com/docs/en/memory)

需要注意，项目指令只是对模型的行为约束，不能代替权限系统、工具审批或服务端校验。

### 10.4 先减少无用输入，再考虑更复杂的压缩方案

对日常编码任务，下面这些操作通常比盲目扩大输入更有效：

- 先搜索符号或关键词，再读取相关代码段。
- 让测试输出保留失败摘要和证据文件位置，避免把几万行成功日志塞进对话。
- 读取文件前检查大小，对大文件分段获取。
- 已经得到充分证据并完成验证时，及时结束任务。

如果工具结果太大，刚总结完又被同一份内容填满，反复压缩也解决不了输入规模本身的问题。应该改变读取范围或结果形态。

### 10.5 压缩后用一个小检查，确认任务还能接上

可以让 Agent 简短回答：

```text
请列出当前目标、必须遵守的约束、已验证事实、尚未完成的工作，以及下一步。
不确定的内容请明确标注，并指出需要重新核验的证据。
```

这份回答能帮助你发现遗漏，但不能自证正确。对接口兼容、数据迁移、部署状态等关键事项，还要与代码、测试和外部状态核对。

## 11. 回到最初的开发任务

再看重复下单的排查：Agent 需要带到下一阶段的，是目标、接口约束、已确认事实、测试证据和未完成事项。几十次搜索和读取的过程可以缩短，关键结论则要有能重新核对的出处。

Codex 与 Claude Code 都在解决这个问题，只是在压缩表示与上下文重建策略上有所差别。对使用者来说，值得关心的是：压缩之后，任务状态能否准确恢复，下一步是否仍然遵守原来的约束。

上下文压缩用部分细节换取会话继续运行。把任务做到可交接、可恢复、可验证，才能让长时间运行的编码 Agent 更可靠。
