你在做一个客服系统。用户发来一句话：

> 同一笔订单被扣了两次钱，请帮我退掉重复扣款。

接下来，程序需要回答几个很具体的问题：这张工单交给谁？影响有多严重？用户是否明确提出了退款？

这些问题不需要一篇分析报告。程序最终需要的，可能只是一个队列名、一个优先级，以及一个可以放进 `if` 的判断。

如果交给聊天模型，它当然能回答。但让模型先写一段文本，再让程序从中提取结果，往往绕了一圈。Jev 关注的正是这一类需求：**把业务状态变成程序可以直接使用的结构化判断。**

这篇文章从工单分流出发，解释 Jev 是什么、为什么值得关注、它与常见 AI 模型有什么区别，再走到概率、开源实现和工程落地。你不需要提前学过机器学习，只需要熟悉接口、条件分支和服务调用。

## 一、Jev 是什么：为软件提供判断结果

Jev 是 TypeSafe AI 推出的结构化决策模型。一次请求主要提供两部分内容：

- **状态（state）**：需要分析的事实，例如用户消息、订单信息、工具执行结果。
- **问题（questions）**：希望作出的判断，以及候选项或评分标准。

输出则是选择、评分或“是”的概率。程序拿到结果后，可以分流、排序、触发复核，或者决定下一步调用什么能力。[官方介绍](https://docs.typesafe.ai/introduction)

可以把它想象成一个接受自然语言条件的判断服务：

```text
输入：业务事实 + 明确的问题 + 允许的答案
输出：结构化结果 + 相关概率
```

它不会因为选中了“退款”就自动退款。**模型负责评估，程序负责决定是否采取动作。**

TypeSafe 把这类模型称为 **System One 模型**，借用了人类“快速、直觉式判断”的说法。这个名字有助于理解其定位，但不是对人脑机制的复现，也不意味着所有问题都能迅速答对。需要长时间推导、多轮调查或生成文字的工作，仍更适合其他工具。[System One 概念](https://docs.typesafe.ai/concepts/system-one)

### 为什么后端工程师值得关心

业务系统中有大量介于硬规则和复杂推理之间的问题。

“订单状态等于已关闭”是确定性判断，直接写代码最好。“这位用户是在催进度，还是要求取消订单？”则需要理解语言，仅靠关键词容易误判。

如果系统每收到一条请求，都需要完成多次这样的语义判断，判断层的延迟、成本和可靠性就会持续影响整条链路。Jev 的价值在于把这种能力做成更适合软件消费的接口。

理解它时，可以先记住一个分工：**规则处理确定性条件，决策模型处理边界明确的语义判断，LLM 处理复杂推理与生成。**

这里的 LLM 是 Large Language Model，即大语言模型。常见的聊天、写作和代码生成模型都属于这个范畴。

## 二、它与聊天模型、传统分类器有什么区别

先看一张比较表。表中描述的是常见使用方式，并非每种模型都只能这样工作。

| 比较点 | 生成式 LLM | 常见的固定标签分类器 | Jev 这类决策模型 |
| --- | --- | --- | --- |
| 主要任务 | 生成、解释、开放式推理 | 预测训练时定义的类别 | 在请求给定的答案空间内判断 |
| 常见输出 | 文字、代码或结构化文本 | 类别及其分数 | 选择、评分、概率 |
| 新增候选类别 | 可以通过提示词描述 | 往往需要调整标签空间并重新训练 | 可以在请求中描述新候选项 |
| 计算方式 | 通常逐步生成输出 Token | 通常一次预测 | 面向直接决策，避免生成回答文本 |
| 延迟特点 | 输出越长，连续解码通常越耗时 | 小型专用分类器往往很高效 | 可减少回答解码成本，仍受模型规模与输入长度影响 |
| 主要边界 | 复杂任务耗时，生成结果仍需校验 | 类别和业务变化会带来维护成本 | 只能在给定信息与答案空间内判断 |

**Token** 是模型处理文本的基本单位，可能是一个词、一个字，或者词的一部分。它不严格等于字符。

这里有两个容易被说过头的地方。

第一，LLM 也能使用 JSON Schema、受约束解码等方式稳定输出结构。不能把区别简化成“LLM 只能写散文，Jev 才能返回 JSON”。更有意义的区别是：系统是否需要生成回答文本，以及它能否提供适合业务使用、经过验证的概率信号。

第二，传统机器学习并非都只能识别固定类别。**零样本分类**指不额外使用新类别的标注样例训练，就尝试识别该类别。它以及文本匹配等方法，都可以通过描述来表达新标签。Jev 的定位是把运行时问题、类型化结果和概率判断放在同一个产品接口中，而不是凭空发明“分类”。

直接决策有机会比生成完整回答更省时，但并不保证比一个专门训练的小分类器更快。选型要比较同一业务上的正确性、维护成本与端到端延迟。

所谓“运行时定义候选项”，也不等于无限泛化。你可以临时增加一个队列，但模型是否理解该队列的业务边界，仍然要用样例验证。

## 三、三个接口：把问题问成程序需要的形状

Jev 提供 `Choice`、`Score`、`Noul` 三类问题。选择接口的依据，是你的程序需要什么形状的答案，而不是哪种名字听起来更智能。

### 1. Choice：从候选项中选一个

工单应交给哪个团队？这是一个选择问题。

```json
{
  "type": "choice",
  "instructions": "选择最适合接收此工单的团队。",
  "criteria": {
    "billing": "支付、扣款、账单和退款问题",
    "technical": "软件故障、接口报错和功能异常",
    "other": "不属于上述团队，或信息不足以确定归属"
  }
}
```

`criteria` 是候选项的定义。键名方便程序使用，描述负责解释业务含义。不要只写 `team_a`、`team_b`，再指望模型知道团队职责。

Choice 返回选中的 `choice`、所有候选项的 `probabilities`，以及 `confidence`。这些概率之和为 1。[Choice 接口](https://docs.typesafe.ai/primitives/choice)

Choice 通常表达“单选”。如果一条消息可能同时涉及退款和取消订阅，而你需要保留两个意图，可以拆成两个 Noul 问题，或者把主路由与附加标签分开处理。

另一个实用习惯是加入 `other` 或复核选项。答案空间里只有“支付”和“技术”时，模型遇到投诉建议也只能在这两项中比较。

### 2. Score：在有顺序的标准上评分

工单中报告的功能受损有多严重？这适合使用 Score。但评分必须围绕一个维度，并且有可区分的标准。

| 级别 | 影响标准 |
| --- | --- |
| 0 | 没有报告功能受损，仅询问、提出建议或请求账务处理 |
| 1 | 报告了功能受损，且明确存在可用的替代方式 |
| 2 | 报告了功能受损，且明确不存在可用的替代方式 |

这套标准衡量的是**已报告的功能受损情况**，不能直接当作工单总优先级。退款金额、处理时限、客户情绪等，应另行判断。未报告功能受损，也不等于已证明系统运行正常。

如果材料说功能受损，却没有说明是否有替代方式，就缺少分档所需的事实。此时应补充信息或转人工，而不是把“没提到替代方式”当成“没有替代方式”。可以另问一个 Noul 检查信息是否充分，由代码决定是否采用 Score；“信息不足”本身也不适合充当严重程度上的某一级。

Score 会给出各级别概率，以及由概率加权得到的分数。假设某次教学示例中的分布为：

```text
P(级别 0) = 0.10
P(级别 1) = 0.60
P(级别 2) = 0.30
```

那么：

$$
\text{score}=0\times0.10+1\times0.60+2\times0.30=1.20
$$

分数 1.20 表示模型在几个等级之间分配了概率，不能解释成“影响了 60% 的用户”。同样的均值，也可能来自不同分布：全部落在级别 1，与一半落在 0、一半落在 2，均值都是 1，但不确定性完全不同。[Score 接口](https://docs.typesafe.ai/primitives/score)

因此，重要决策不要只读取最终分数。还要看完整分布、置信信息，以及最高风险等级是否有值得关注的概率。

写评分标准时，尽量描述具体情形。“轻微、一般、严重”通常不如“存在替代方式”“核心流程无法继续”清楚。每个等级都应能独立理解，避免写“比上一级更严重”。

### 3. Noul：判断一个命题是否成立

用户有没有明确提出退款？这是一个可以回答“是或否”的命题。

```json
{
  "type": "noul",
  "instructions": "用户是否明确要求退还款项？仅询问退款政策不算提出退款。"
}
```

Noul 返回一个 0 到 1 的 `noul` 值，表示“是”的概率。接近 1 倾向于是，接近 0 倾向于否，接近 0.5 则缺乏明确倾向。它没有独立的 `confidence` 字段。[Noul 接口](https://docs.typesafe.ai/primitives/noul)

例如，`noul = 0.8` 表达的是“提出了退款请求”的概率，而不是“退款意愿有八成强烈”。前者是命题的不确定性，后者是程度，应该另行定义评分标准。

对于证据缺失的情况，也不要把低概率直接解释成“事实已被证明为假”。模型只能根据收到的材料判断；业务可能还需要明确的“信息不足”流程。

## 四、先接一次 API，再把判断接进代码

把下面内容保存为 `request.json`。它围绕同一条工单，一次提出三个问题：

```json
{
  "model": "jev-latest",
  "state": "同一笔订单被扣了两次钱，请帮我退掉重复扣款。",
  "questions": {
    "team": {
      "type": "choice",
      "instructions": "选择最适合接收此工单的团队。",
      "criteria": {
        "billing": "支付、扣款、账单和退款问题",
        "technical": "软件故障、接口报错和功能异常",
        "other": "其他问题或信息不足"
      }
    },
    "impact": {
      "type": "score",
      "instructions": "只评估已报告的功能受损情况，不评价退款金额或客户情绪。",
      "criteria": [
        "没有报告功能受损，仅询问、提出建议或要求处理账务",
        "报告了功能受损，且明确存在可用的替代方式",
        "报告了功能受损，且明确不存在可用的替代方式"
      ]
    },
    "refund_requested": {
      "type": "noul",
      "instructions": "用户是否明确要求退还款项？仅询问退款政策不算。"
    }
  }
}
```

如果使用下载包，请先进入 `jev-demo/examples/`；如果手动练习，在保存 `request.json` 的目录执行。取得 API Key 并设置环境变量后，可以这样调用：

```bash
curl --fail-with-body --silent --show-error --max-time 15 \
  https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer ${TYPESAFE_API_KEY:?请先设置 TYPESAFE_API_KEY}" \
  -H "Content-Type: application/json" \
  --data-binary @request.json \
  -o response.json
```

请求方式依据[官方 Quick start](https://docs.typesafe.ai/introduction/quickstart)。`--fail-with-body` 需要 curl 7.76 或更新版本。`jev-latest` 适合快速试用；需要稳定回放时，应记录实际返回的模型版本，并在服务支持的情况下固定版本。中文效果也应单独评估。

这里共享的是 `state`。每个问题独立对这份事实作判断，不会先读取另一个问题的答案。因此，“先判断团队，再根据该答案重新提出后续问题”仍需由程序编排，不能靠同一请求里问题的书写顺序实现依赖。

下面演示程序如何读取一个 Choice 结果。**这里的概率是教学构造，并非真实 API 返回；阈值也只是展示分支逻辑。**

```python
answer = {
    "choice": "billing",
    "probabilities": {"billing": 0.92, "technical": 0.05, "other": 0.03},
    "confidence": 0.88,
}

def route(answer):
    selected = answer["choice"]
    p_selected = answer["probabilities"][selected]
    if selected == "other" or p_selected < 0.70:
        return "human_review"
    if p_selected < 0.90:
        return "collect_more_context"
    return {"billing": "billing_queue", "technical": "technical_queue"}[selected]

print(route(answer))  # billing_queue
```

这段代码只负责低风险的工单分流。它没有根据“用户要求退款”直接执行退款，因为**表达意图、符合退款条件、具备执行授权，是三个不同判断**。

真实 API 的各个答案放在顶层 `answers` 对象中，使用请求里定义的 `team`、`impact` 等问题名作为键。运行前面的 curl 后，可以接着读取保存的响应，并调用同一个 `route` 函数：

```python
import json
from pathlib import Path

response = json.loads(Path("response.json").read_text(encoding="utf-8"))
answers = response["answers"]
print("工单去向：", route(answers["team"]))
print("功能受损评分：", answers["impact"]["score"])
print("提出退款请求的概率：", answers["refund_requested"]["noul"])
```

这里打印分数是为了展示字段读取；是否采用该分数，仍要检查评分所需的信息是否充分。字段层级见[官方响应示例](https://docs.typesafe.ai/introduction/quickstart)。

真实接入还应校验响应结构、候选键、数值范围，并为超时或服务异常指定降级路径。接口格式可预测，不代表网络和外部依赖永远成功。

配套的 `examples/` 目录提供请求文件、调用脚本和可离线运行的分流示例，均收在[完整学习包](#download)中。本文未使用真实 API Key 进行在线推理，所有演示数值均不构成模型效果测评。

## 五、为什么不用生成文字，也能作出判断

先从生成式模型的常见工作方式理解。

模型读取输入后，估计下一个 Token 的分数，选出一个 Token，再把它接回上下文，继续计算后面的 Token。这种依赖前文、逐步生成后文的方式，叫作**自回归生成**。

即使你只需要一个队列名，模型也可能要生成字段名、引号、分隔符和答案内容。如果开启较长的推理输出，还会产生更多步骤。

对于候选项明确的问题，可以换一种输出方式：**直接为允许的选项打分，再转换成概率，不继续生成回答文本。**

![生成式路径与直接决策路径：直接决策省去连续生成回答文本的步骤](01-decision-path.png){: width="1600" height="1000" }

### 从 logits 到概率

模型给每个候选项算出的原始分数，常叫作 **logit**。它可以为正，也可以为负，本身不是概率。

假设三个候选项的 logits 是 `[3.0, 1.0, 0.0]`，可以用 softmax 把它们转换成和为 1 的概率：

$$
p_i=\frac{\exp(z_i/T)}{\sum_j\exp(z_j/T)}
$$

其中，`z_i` 是第 `i` 个候选项的 logit；`T > 0` 称为温度，先取 1 即可。

下面只用 Python 标准库演示这一步：

```python
import math

def softmax(logits, temperature=1.0):
    if temperature <= 0:
        raise ValueError("temperature 必须大于 0")
    scaled = [z / temperature for z in logits]
    peak = max(scaled)  # 减去最大值，避免指数计算溢出
    weights = [math.exp(z - peak) for z in scaled]
    total = sum(weights)
    return [w / total for w in weights]

print([round(p, 3) for p in softmax([3.0, 1.0, 0.0])])
# [0.844, 0.114, 0.042]
```

这只是“分数转概率”，没有实现语言理解。理解工单与选项，需要前面的模型计算。

另外，softmax 只是在所给候选项之间分配概率。它不会自动检查答案空间是否完整。哪怕三个选项都不合适，概率仍然会加起来等于 1。

### 一次前向计算，不等于一次计算什么都能解决

**前向计算**指输入经过模型各层，得到输出的过程，与训练时用于更新参数的反向传播相区分。

不少开源决策模型可以在一次前向中给多个选项打分。但“一次前向”仍可能涉及数十亿参数和很长的输入，并不天然等于低延迟。实际耗时还包括输入处理、显存访问、批处理、排队和网络。

对 Jev，公开文档能确认的是类型化决策接口和不生成回答文本的定位。开源项目中常见的“一次前向”“读取下一 Token logits”是可研究的实现路线，不能直接当作对 Jev 内部架构的定论。

## 六、概率校准：0.9 应该如何经得起验证

如果接口只输出一个标签，程序很难从结果中判断模型有多犹豫。增加概率后，程序可以更精细地控制行为：高把握自动处理，中等把握补充信息，低把握转人工。

TypeSafe 把校准概率列为决策模型的训练目标之一。[官方 AI primer](https://docs.typesafe.ai/introduction/machine-learning-primer) 但要把概率用于业务门槛，仍需验证它在自己数据上的可靠性。

### 准确率与校准，关注的不是同一个问题

**准确率**关注模型选对了多少次。**概率校准**关注模型给出的概率，与长期实际发生频率是否匹配。

例如，把“所选答案的预测概率在 0.85 到 0.95 之间”的工单收集成一组。如果平均预测概率约为 0.9，那么这组答案的实际正确率也应接近 90%。这是一种群体统计关系，不能保证某一条工单一定正确。[概率校准研究](https://arxiv.org/abs/1706.04599)

一个分类器完全可能选得相当准，却经常对错误答案给出接近 1 的概率。这样的模型不适合仅靠高概率放行。

![概率校准教学图：预测概率与实际正确率应接近，过度自信时曲线落在对角线下方](02-calibration.png){: width="1600" height="1000" }

*图 2：以 Choice 所选答案的概率为例。曲线和数据均为教学构造，不是 Jev 或任何开源模型的实测结果。*

不同输出要对不同的事实“对账”。Choice 可以按所选答案的预测概率分组，与该组的选择正确率比较；Noul 要把“是”的预测概率，与该组真实为“是”的比例比较。例如 `noul = 0.1` 应对应约 10% 的“是”，不能解释成判断正确率只有 10%。Score 则可以逐等级检查预测概率，不能把最终分数直接当作正确概率。

### 不要把 API 的 confidence 当成正确率

Jev 的 `Choice`、`Score` 返回的 `confidence`，是根据答案概率分布计算出的统计量，不是另一个“保证正确”的模型结论。按照当前官方定义，Choice 的计算为：

$$
\text{confidence}=\frac{p_{\max}-1/n}{1-1/n}
$$

其中 `n` 是选项数量。因此，三个选项中最高概率为 0.92 时，`confidence` 为 0.88。这两个数表达的含义不同。Score 的置信统计还考虑等级之间的距离；Noul 则没有单独的该字段。[官方置信度定义](https://docs.typesafe.ai/confidence)

所以，“`confidence = 0.9` 就意味着历史正确率必须是 90%”不是严谨的解释。要验证预测概率是否校准，应对相应事件或所选答案的预测概率分组，再与真实标签对账；若用 `confidence` 作业务门槛，则需要测出各门槛下的实际错误率。

### softmax 不会自动带来校准

softmax 保证数值具有概率分布的形式，却不保证预测频率可信。

一种常见的后处理方法是**温度缩放**：在独立验证集上拟合上面公式中的 `T`，再用它调整概率分布。在固定 logits 上使用同一个正温度，不会改变 Choice 的最大分数选项，但会改变概率；也可能改变按期望计算的 Score，以及依赖阈值的决策。[温度缩放方法](https://arxiv.org/abs/1706.04599)

校准集与最终测试集要分开。换了语言、候选项定义、模型版本或业务分布，也应重新检查，不能把某个基准上的校准表现当作永久承诺。

整体校准接近，也不代表每个子场景都可靠。例如普通咨询与退款工单可能有不同的误差，高风险类别应单独查看概率分组与实际结果。

### 阈值应由错误代价决定

把工单分错队列，通常可以纠正；错误触发资金操作，代价就大得多。两者不该共用一个“高于 0.8 就执行”的规则。

对于简单的二元判断，可以先从成本关系理解阈值。假设只考虑误报和漏报：误报成本为 `C_FP`，漏报成本为 `C_FN`，预测“是”的可靠概率为 `p`，则：

$$
\text{判为是的期望损失}=(1-p)C_{FP}
$$

$$
\text{判为否的期望损失}=pC_{FN}
$$

选择较小损失，对应的阈值是：

$$
p>\frac{C_{FP}}{C_{FP}+C_{FN}}
$$

这说明：漏掉风险越昂贵，触发复核的阈值可能越低；错误执行越昂贵，执行门槛应越谨慎。现实系统还有人工成本、延迟和授权约束，这个简化公式用于解释方向，不能直接替代完整策略。

## 七、开源实现怎么做：三条常见技术路线

“开源复刻”通常复现的是**输入状态与候选项、输出类型化概率**的使用方式。接口相似，并不能证明它复现了 Jev 的训练方法、内部架构或实际能力。

下面三种做法并非完全互斥：A 侧重怎样读取答案，B 侧重怎样增加打分结构，C 侧重选择什么骨干架构。编码器也可以加决策头；LoRA 则是训练方法，可以与不同的读出结构组合使用。

### 路线 A：直接读取现有 LLM 的候选 logits

假设在提示中把团队映射成三个代码：

```text
A：支付与退款
B：软件故障
C：其他
```

模型处理完输入后，读取答案位置上 `A`、`B`、`C` 的 logits，只对这几个数做归一化，然后映射回业务键名。整个过程无需先生成完整答案句子。

这条路线适合建立基线，因为可以先不训练模型。但有几个实现细节决定它是否可靠：

- **答案代码应在实际上下文中是单 Token。** 如果某个标签被切成多个 Token，只比较第一个 Token，会漏掉后续信息。
- **概率是受候选集合条件化的。** 在几个答案代码内重新归一化，不等于获得开放世界下“答案一定正确”的概率。
- **提示模板和候选顺序可能影响结果。** 更换顺序、代码或模型版本后，应检查结果是否稳定。

SemIf 就提供了这种直接读取候选概率的开源基线。[SemIf 项目](https://github.com/TheoLeeCJ/SemIf-OpenJev)

### 路线 B：预训练骨干模型，加上轻量决策头

**骨干模型**是负责把文本转成内部表示的主要网络。这里的表示通常是向量，也就是一组用于编码信息的数值。**决策头**是接在这些表示后面的较小网络，负责给问题和候选项打分。

要支持动态候选项，不能只在末尾放一个固定三类分类器。模型需要接收候选项的语义描述，或者采用能对不同选项重复使用的打分结构。

**预训练**是在大量通用数据上训练模型，让它先学到语言规律；**微调**是在已有模型上，用特定任务的数据继续训练。预训练骨干提供已有的语言知识，决策头学习“如何按这些标准作判断”。必要时也可以联合微调骨干，让内部表示更适合任务。

另一种适配方法是 **LoRA（低秩适配）**：冻结原有大部分权重，训练少量新增参数，降低微调所需的训练资源。它有助于利用已有语言能力，但不是“不损失通用能力”的保证，仍需验证迁移后的表现。[LoRA 原始论文](https://arxiv.org/abs/2106.09685)

### 路线 C：使用双向编码器直接打分

**编码器**把输入转成向量表示；**双向**表示某个位置的表示可以利用它前后两侧的信息。对于“通读材料后判断哪一项更合适”的任务，这种结构很自然。

它不需要为开放式续写保留完整的生成流程，可以围绕分类与判断设计输出。Laya 使用 ModernBERT、mmBERT 等编码器提供不同检查点，包含面向多语言的路线。[Laya 项目](https://github.com/NandhaKishorM/laya)

但双向编码器并非天然理解更强，参数较小也不代表所有场景都更快。输入长度、语言覆盖、训练数据和部署方式，都会影响结果。

### 多个问题怎样共享上下文

假设一份很长的工单背景，需要回答 10 个独立问题。每个问题都重新读取一次全文，会重复消耗大量计算。

一种优化是先处理共同前缀，缓存可复用的中间状态，再分别计算问题部分。**注意力机制**用于让模型按相关性聚合不同位置的信息；LLM 中常见的 **KV Cache**，就是缓存这类计算中的 Key、Value 等状态，以减少重复工作。具体模型还可能需要其他状态。

另一种实现通过批处理、特殊注意力掩码或专门的打分结构，组织多个判断。

这些方案都可能提高吞吐，但不能简单说成“10 个问题永远等于 1 个问题的成本”。缓存是否命中、问题数量、输入长度、显存与并发负载，都会影响收益。共享事实也不等于共享答案：有依赖的问题，仍需显式编排。

## 八、开源项目该怎么看

理解了技术路线，再看项目就不必只比较名字和宣传延迟。下面按学习价值介绍四个项目与两个相关方向；项目能力以其具体版本和官方仓库为准。

模型名称里的 `9B` 表示约 90 亿个参数；参数是模型训练得到的数值。**检查点（checkpoint）**是保存下来的一版模型参数及相关配置，可以理解为模型的可加载版本。

| 项目 | 主要特点 | 适合研究的问题 |
| --- | --- | --- |
| [Kev](https://github.com/jaredpalmer/kev) | 多种模型规模；兼容 TypeSafe System One API，可让 TypeSafe Python SDK 指向本地服务 | 如何在现有调用链中接入本地决策模型 |
| [Nimble](https://github.com/bespokelabsai/nimble) | 基于 Qwen3.5-9B 做 LoRA 微调；开放数据、训练与评估流程 | 如何用精细的数据改善语义判断 |
| [Laya](https://github.com/NandhaKishorM/laya) | 编码器与决策头路线，提供英语、多语言等检查点 | 如何围绕判断任务设计较紧凑的模型 |
| [SemIf](https://github.com/TheoLeeCJ/SemIf-OpenJev) | 曾用名 OpenJev；直接读取开放模型的候选 logits | 不训练时怎样建立基线，以及如何复用状态 |

### Nimble 的一个教学重点：最小对比数据对

设想两条只改变一个关键事实的材料：

```text
样例 A：订单尚未发货，用户明确要求取消。
样例 B：订单已经发货，用户明确要求取消。
```

再给出业务规则：“尚未发货且用户明确要求取消，才允许走自动取消流程。”

两条材料的措辞几乎一样，但正确判断应该相反。这样的**最小对比数据对**，用来训练和检查模型是否跟随决定性的事实变化，而不是只看见“要求取消”就给出同一个答案。

Nimble 的数据流程包含局部事实变化与成对校验。真正困难的部分是确保只改变了预期事实，答案也确实随之变化；简单限制编辑字数并不能证明语义上只改了一个事实。上面的订单案例是本文构造的解释例子。[Nimble 数据构造说明](https://github.com/bespokelabsai/nimble/blob/main/docs/TRAINING_EVAL_CURATION.md)

### 两个相关方向：高并发服务与极简原型

[openjev-sglang](https://github.com/ekzhang/openjev-sglang) 更适合研究推理服务：利用模型推理与服务框架 SGLang 的前缀缓存复用共同输入，再并发处理问题分支。其当前实现为缓存预热和各问题请求一个 Token，忽略采样内容，使用候选标签的概率；它并不是把所有问题压成一次模型调用，也不是完全不触发采样的专用决策头。

[Jevlike](https://github.com/vinnylarouge/jevlike) 则适合学习小型打分模型：把选项转为查询向量，从上下文聚合信息，再给每个选项打分。轻量结构便于读懂与实验，但不意味着默认模型已经具备成熟大模型的语义能力。

开源社区有多个名称近似的 OpenJev、Open-Jev 项目。本文表格中的 SemIf 指明确链接的那个项目，避免把同名项目的结构、评测和能力混在一起。

如果准备替换服务，建议沿着三个层次检查：

1. **接口是否兼容**：字段、错误码、超时和 SDK 行为能否对应。
2. **业务是否可用**：语言、边界样例和候选变化下是否判断正确。
3. **概率是否可信**：现有阈值是否仍成立，错误率能否接受。

接口兼容，只能证明调用方式接得上。校准表现和语义能力需要分别验证。自部署还要计算硬件、运维、模型下载与许可成本。

## 九、三个落地入口：路由、护栏和上下文压缩

先解释一个词：**Agent** 可以理解为一个围绕目标组织模型、工具和状态的程序。它可能搜索资料、调用订单接口、读取工具结果，再决定下一步做什么。它不一定是某一个模型，更像一套会利用模型作判断的工作流。

Jev 可以成为这套程序中的判断层。

### 1. 意图路由：把请求交给合适的处理器

如果后端服务有账务、技术支持和账户管理几个处理器，就可以把它们描述为候选项，由 Choice 选出主路由。

在 Agent 系统中，接收方也可能是一个 **Sub-agent（子代理）**：一个只负责特定领域、拥有相应上下文和工具的处理单元。

合理流程是先通过规则过滤不可用的接收方，再判断语义归属，最后按概率决定直接分流还是复核。例如，某个子代理只支持英文，就不应在中文请求的候选集合中参与竞争。

工具选择也类似。程序先筛出当前用户有权使用、参数条件满足的工具，模型再在合法候选项中选择。模型选中了某工具，并不会创造使用权限。

### 2. 安全护栏：执行前后分别判断

“安全护栏”指在系统关键位置检查输入、动作或输出，减少不合适行为。

执行前，可以评估：“拟执行动作是否超出了用户这次明确提出的需求？”执行后，可以评估：“返回内容是否包含不应展示的敏感信息？”内容审核、风险识别，都属于这种语义判断的应用。

但确定性的权限校验必须由程序完成。租户隔离、资源所有权、金额上限、操作授权，不能仅靠模型说“看起来没问题”。模型也可能受到输入中的诱导内容影响，不能把待分析文本当作可信策略。

一个可靠的设计会把用户原话、拟执行工具、参数、明确授权范围与规则一起提供给判断层，并把模型结果当作附加风险信号。高风险或信息不足时，可以直接转人工，不必先经过另一个模型。

**失败后的重试或停止**也可以接入判断层，但要先区分确定性错误：

- 参数校验失败、权限不足，通常应修正或停止，不能盲目重试。
- 可恢复的网络或服务故障，可以按既定退避、次数和预算策略处理。
- 错误信息语义模糊时，可以让模型辅助选择“补充信息、改用其他工具、停止”。

尤其是具有副作用的操作，超时不代表执行失败。重试之前必须查询执行状态或利用幂等机制，不能让“模型建议重试”导致重复扣款或重复创建记录。

### 3. 上下文压缩：保留对当前问题有用的历史

**上下文**是当前请求中实际提供给模型的信息。历史对话越长，处理成本越高，也越容易混入无关内容。

可以针对每条历史消息，用 Score 评估它与当前问题的相关性，例如：

```text
0：与当前任务无关
1：提供背景，但不会改变当前判断
2：直接提供完成当前任务所需的事实
```

再按分数与 Token 预算选择保留内容。这更接近“筛选上下文”，并不会自动生成一份忠实摘要；需要摘要时，可以让生成式模型处理保留的信息。

实际使用要先保护关键状态：用户约束、授权记录、已完成动作、订单标识、工具调用与结果之间的对应关系。不能因为某条授权记录对当前句子的表面相关性不高，就把它丢掉。

压缩质量最终要看下游任务是否仍能正确完成，而不只是上下文减少了多少 Token。为了筛选而额外产生的判断成本，也要一起计算。

## 十、怎样把它接进一个可维护的系统

不必把全部业务逻辑改成模型调用。可以先挑一个高频、答案明确、错误容易纠正的判断点，例如工单主队列分流。

![规则、Jev、LLM、执行器与人工之间的协作架构](03-agent-architecture.png){: width="1600" height="1090" }

*图 3：一种可选的工程分工。LLM 按需补充推理与生成能力，人工可直接接管不确定或高风险事项。*

### 先把问题定义清楚

“这个客户值不值得优先服务？”混合了收入、紧急程度、影响范围和服务承诺，很难稳定标注。

可以拆成“是否有合同规定的服务时限”“核心业务是否受阻”“是否已有替代方案”等判断，再由代码组合结果。其中，能通过数据库精确查询的条件，直接查询，不必交给模型猜。

多维评分要合成一个优先级时，应先统一量纲。例如三档 Score 的范围是 0 到 2，五档是 0 到 4，不能未经归一化就直接加权。权重与业务规则应保留在代码中，便于解释和调整。

### 用业务样例同时验证正确性和不确定性

准备标注数据时，要包含常见输入，也要包含多意图、信息缺失、反例、中文口语和相近候选项。可加入成对样例，例如“要求退款”与“询问退款政策”，检查模型是否真正区分了业务边界。

训练、校准与测试应划分清楚；同一工单的改写或同一客户的高度相似记录，尽量不要跨集合泄漏。否则离线成绩会高估实际效果。

关键指标至少包括：

| 需要回答的问题 | 观察指标 |
| --- | --- |
| 是否选对了 | 准确率、各类精确率与召回率 |
| 自动处理的部分是否可靠 | 自动处理覆盖率，以及这部分的错误率 |
| 概率是否可信 | 概率分组与实际正确率的差异，可辅以 Brier 分数或 ECE |
| 是否真的更快、更省 | 端到端 p50/p95 延迟、单次成功决策的总成本 |
| 出故障后能否接住 | 超时、错误响应和降级路径的表现 |

精确率关注“模型判为某类的样例中，有多少真的属于该类”；召回率关注“真实属于该类的样例中，模型找到了多少”。两者可帮助发现总体准确率掩盖的少数类问题。

**Brier 分数**衡量预测概率与真实标签之间的平方误差，数值越低越好，但它不只反映校准。**ECE** 把预测分组后，汇总概率与实际正确率之间的差距；它受分组方式和样本量影响。数据较少时，应结合分组样本数和具体错误分析，避免迷信单个数字。

比较速度时，用同样的输入、问题数量、准确性要求和部署条件。只比较本地模型推理耗时与跨网络 API 总耗时，或者只比较首 Token 时间与完整回答时间，都容易得出偏差结论。

### 逐步放量，保留回放所需的信息

可以先让新判断层在后台产生建议，与现有处理结果对比；验证后再开放低风险自动分流。

记录至少应包含模型版本、问题与候选项版本、输入来源标识、返回概率、实际采用的分支和后续纠错结果。日志中的原始内容按业务需要脱敏或受控保存。

这样某一类工单突然频繁分错时，才有办法分清：是业务输入变了，候选定义重叠了，模型升级了，还是阈值失效了。

## 十一、几个常见误区

**“不生成文本，就不会幻觉。”**

限制答案空间，可以减少模型随意输出不存在的类别或破坏格式的问题，却不能消除语义错误。它仍可能在几个合法选项里，自信地选错。

**“高置信度就是可以自动执行。”**

置信统计只是决策依据之一。执行还受授权、事实完整性、错误代价和业务状态约束。模型不应凭一个数值获得额外权限。

**“候选项越多，就越通用。”**

候选数量增加，也可能带来近义类别、边界重叠和输入变长。先把选项定义清楚，再考虑扩展。缺失合理答案时，增加模型大小也解决不了答案空间问题。

**“Jev 可以替代 LLM。”**

当任务是解释故障原因、跨多份资料推导结论、写回复或生成代码时，单个结构化判断并不够。更合理的方式，是让不同能力负责各自擅长的部分。

**“开源项目返回一样的 JSON，就能直接替换。”**

同样的 JSON 外形，背后可能是完全不同的模型、训练数据和概率定义。接口、业务表现、校准和服务稳定性，都需要各自的证据。

## 写在最后：先找到系统里那个反复出现的小判断

对后端工程师来说，Jev 最值得借鉴的不是一个新名词，而是一种设计习惯：把“理解一段业务事实”与“执行一项业务动作”分开，让模型提供可检查的判断，让程序保留明确的控制逻辑。

下次准备让大模型生成一段 JSON 时，可以先检查真正需要的答案：它是一个路由、一个有标准的评分，还是一个具体命题的概率？

如果答案空间清楚、调用频繁、需要较低延迟，结构化决策模型值得作为候选方案。若连团队成员都难以说明怎样算判断正确，就先澄清问题与规则。一个能被清楚定义、验证和回放的判断，才适合进入自动化链路。
