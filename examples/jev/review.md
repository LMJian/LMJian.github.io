# Jev 入门博客复审记录

复审日期：2026 年 10 月 23 日。

通读了正文、配套代码和配图，并将用户提供图片中的内容拆为 38 个核对项；重新查询 TypeSafe 官方文档及对应开源项目仓库。

**结论：原稿没有整块核心主题遗漏，但存在评分示例、概率解释和教学闭环上的改进空间。以下六类问题已修正，Markdown 与完整下载包同步更新。**

## 发现的问题与修改

| 问题 | 原稿可能造成的误解 | 本次修改 |
| --- | --- | --- |
| Score 分档不够完整，评分维度不够清楚 | “非核心功能受损且无替代方案”难以落档；功能受损分数可能被当成工单总优先级 | 把高两档统一到“功能受损”，按是否有替代方式区分；说明金额、时限等另行评估；信息不足时补充信息或转人工 |
| 校准说明还需区分输出类型 | 把 Noul 的“是”的概率与判断正确率混为一谈，或把 Score 本身当作正确概率 | 分别说明 Choice 的选择正确率、Noul 的实际为是比例、Score 的逐等级概率；配图明确限定为 Choice 示例；提醒整体校准不保证每个子场景都可靠 |
| API 示例没有接到真实响应读取 | curl 保存了 response.json，但后面的路由始终读取手写教学对象 | 增加 answers 层级读取示例；配套程序支持 --response，仍保留无需凭据的离线模式 |
| 三条技术路线并非互斥分类 | 误以为 logits 读取、决策头、编码器和 LoRA 只能择一 | 说明它们分别涉及读出方式、结构和训练方法，可以组合 |
| Kev 的 SDK 兼容性描述偏弱 | 只知道 API 形状兼容，不知道可复用 TypeSafe Python SDK | 明确写出把 SDK 指向本地服务的能力，同时保留“接口兼容不等于效果等价”的边界 |
| 面向零基础读者的少量解释不足 | “零样本”未解释；可能误以为决策模型必然比小分类器快 | 增补零样本定义、延迟比较，以及同业务条件下选型的提醒 |

Score 的问题属于本文自定义示例的设计缺陷，不是对 Jev 官方接口能力的否定。真实响应读取路径已使用构造的 API 格式响应验证，未冒充线上推理验证。

## 核查后保留的正确表述

- `confidence` 与所选答案的预测概率不同。当前官方 Choice 公式下，三个选项、最高概率 0.92，对应 confidence 0.88；Noul 没有独立 confidence 字段。[TypeSafe Confidence](https://docs.typesafe.ai/confidence)
- 对 Jev 的“一次前向”不作未经证实的内部结构断言；说明开源实现的实际计算路径，属于必要的事实边界，不是遗漏该知识点。
- SemIf 是所链接项目的当前名称，曾用名 OpenJev；同名或近名仓库不能混为一谈。[SemIf 仓库](https://github.com/TheoLeeCJ/SemIf-OpenJev)
- openjev-sglang 的文档写明 N 个问题包含 N+1 次单 Token 请求，不能说成“一次模型调用回答所有问题”。[openjev-sglang 仓库](https://github.com/ekzhang/openjev-sglang)
- 更稳定的输出格式不保证判断正确；规则、决策模型、LLM 与人工的分工、执行授权和重试幂等边界应保留。
